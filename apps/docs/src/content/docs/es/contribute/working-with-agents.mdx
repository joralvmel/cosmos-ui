El repositorio incluye un equipo de agentes especializados (`.github/agents/`) y skills paso a paso
(`.github/skills/`, cada una con un prompt en `.github/prompts/`). Siguen `AGENTS.md`, las reglas de
`.github/instructions/` y la [anatomía de componentes](https://github.com/joralvmel/cosmos-ui/blob/develop/docs/conventions/component-anatomy.md).

## Cómo usarlos en VS Code

1. Abre el repositorio en VS Code con GitHub Copilot y abre la vista **Chat**.
2. **Agentes**: elige uno en el selector de agentes del chat (por ejemplo `component-builder`) y
   describe la tarea. El agente carga sus reglas y usa sus skills.
3. **Prompts**: escribe `/` y el nombre de la skill, por ejemplo `/create-component`,
   `/component-status` o `/start-work`. El prompt pide sus datos y ejecuta la skill con el agente
   adecuado.
4. Añade contexto con `#` (un archivo, una carpeta o un enlace de Figma) cuando ayude.

Otros asistentes (Codex, Claude Code, Cursor…) leen `AGENTS.md`; indícales una skill, por ejemplo
"sigue `.github/skills/create-component/SKILL.md` para `switch`".

## Investigación, decisiones y revisión local

Sigue el [flujo de componentes](https://github.com/joralvmel/cosmos-ui/blob/develop/docs/conventions/component-workflow.md).
El chat principal coordina a los especialistas y mantiene contigo las decisiones:

1. El investigador compara estándares e implementaciones públicas, con licencias, diferencias entre
   plataformas y costes. Su recomendación no autoriza a implementar todas las opciones.
2. Copilot presenta requisitos, funciones recomendadas y mejoras opcionales; después pregunta en
   bloques pequeños sobre diseño y API. Apruebas qué se incluye, excluye o aplaza **antes de generar
   archivos o editar el contrato**. Los ejemplos no se convierten sin consultarte en casos especiales
   ni listas exclusivas de valores admitidos.
3. Los agentes implementan lo acordado y ejecutan las comprobaciones. El informe distingue navegador
   e integración real de wrappers, React Native Web, mocks, builds y ejecución en Android/iOS.
   Las herramientas, dispositivos o pruebas de lector de pantalla no disponibles se indican; no se
   marcan como aprobadas.
4. `finish-work` valida y crea automáticamente un **commit local**, comunica su SHA y cómo probarlo,
   y **espera sin hacer push ni PR**. Puedes pedir ajustes para otro commit y otra pausa, o aceptar
   ese commit concreto para que `open-pr` haga push y abra o reutilice la PR.

Pedir al principio que implemente y termine abriendo una PR no aprueba cambios que aún no has visto.
Aprobar las funciones no equivale a aceptar la implementación. Si cambia HEAD, debes volver a
validarlo; el agente no modifica commits anteriores con amend por defecto.

Los agentes de pruebas y nativo incluyen herramientas de navegador, y los roles coordinadores pueden
delegar y hacer preguntas interactivas. Su disponibilidad depende del harness y las herramientas
habilitadas. El flujo no omite permisos del editor ni añade una aprobación obligatoria en GitHub.

## Qué pedirles

- **Una tarea cada vez**, con el resultado que esperas: "Crea el componente `switch` para todas las
  plataformas" mejor que "trabaja en formularios".
- **Da referencias**: un número de issue, un enlace de Figma, un patrón de la WAI-ARIA APG.
- **Déjales validar**: la implementación incluye tests y
  `npx biome ci . && npx turbo run typecheck test build`. Una investigación entrega fuentes, no
  resultados de tests inventados. Pide las evidencias y las comprobaciones no disponibles.
- **Revisa antes de integrar**: pide a `reviewer` una revisión de la rama.
