Usa estos prompts en el **chat principal abierto en este repositorio**. Ese chat coordina a los
especialistas; no necesitas cambiar de agente en cada paso. Puedes escribir en lenguaje natural,
sin un comando con `/`. Nombres como `create-component` son skills existentes, no comandos nuevos.

Sustituye los valores entre `[corchetes]` y adjunta los archivos, capturas, issues o logs relevantes.
Elimina lo que no aplique; nunca pegues credenciales ni datos privados en un prompt.

### Qué incluye toda implementación

El [flujo de componentes](https://github.com/joralvmel/cosmos-ui/blob/develop/docs/conventions/component-workflow.md)
ya exige aprobar el alcance de nuevos comportamientos tras investigar, mantener la paridad del
contrato y las plataformas, pruebas adecuadas, docs EN/ES, referencias de IA y changesets para los
paquetes publicables modificados. Corregir un bug concreto dentro del contrato aceptado no requiere
otra entrevista de funcionalidades.

La implementación termina con un **commit local validado y una pausa**. Ni el prompt inicial ni
la aprobación del alcance autorizan push, PR, merge o release. Investigar o revisar en modo solo
lectura no autoriza ediciones ni commits. Si falta un navegador, dispositivo o herramienta, el
agente debe indicarlo en vez de dar la comprobación por superada.

## Empezar un componente

### Explorar el catálogo

Úsalo si quieres recomendaciones, todavía no una implementación.

```text
Revisa el inventario actual de componentes y sus dependencias. Recomiéndame tres candidatos
para crear después, ordenados por utilidad, esfuerzo y lo que desbloquean. Investiga el candidato
más prometedor y distingue funciones obligatorias, recomendadas y opcionales, con fuentes y
diferencias entre plataformas. Presenta las decisiones que debería tomar a continuación.
Es una tarea de solo lectura: no generes archivos, no hagas commit ni push.
```

### Crear desde una necesidad

`badge` es un ejemplo, no una petición de añadir todas las funciones que aparezcan al investigar.

```text
Crea el componente badge siguiendo create-component. El objetivo es comunicar un estado breve
o un recuento en web, React, Angular y React Native.

Revisa el inventario e investiga primero. Recomienda un alcance inicial útil y después pregúntame
en bloques pequeños sobre variantes, tamaños, personalización, contenido, accesibilidad y
diferencias entre plataformas. Explica qué incluir, excluir o aplazar; espera mi aprobación antes
de generar archivos o editar el contrato.

Tras aprobarlo, implementa y valida lo acordado end-to-end, con controles representativos en las
demos. Crea un commit local, muestra el SHA y cómo probarlo, y espera sin hacer push ni PR.
```

### Crear desde un diseño

Una captura no especifica el teclado, la propiedad del estado ni todas las interacciones nativas.

```text
Usa component-from-design para [componente] con esta referencia: [enlace al frame de Figma o captura].
El uso previsto es [necesidad del usuario]. Comprueba si ya existe un componente que lo resuelva.

Investiga el patrón de interacción y relaciona el diseño con los tokens actuales. Indica qué
define la referencia, qué falta y qué diferencias entre plataformas requieren una decisión.
Pregúntame antes de elegir comportamientos no visibles o añadir tokens/dependencias. Espera la
aprobación del alcance y diseño, y completa lo acordado en todas las plataformas aplicables.
Valida, crea un commit local y espera mi revisión.
```

## Evolucionar un componente existente

### Ampliar el comportamiento

Describe el resultado para el usuario antes de imponer un nombre de prop. Si la capacidad ya
existe, el agente debe explicar cómo usarla en vez de crear otra API.

```text
Usa modify-component para [componente]. Necesito que el usuario pueda [resultado deseado].
Ejemplo de uso: [entrada, interacción y resultado esperado].

Revisa primero la API, los escenarios y la documentación actuales. Si ya está soportado, explícame
cómo usarlo y no hagas cambios innecesarios. Si no, investiga alternativas, recomienda una API y
explica compatibilidad, accesibilidad y diferencias web/nativo. Pídeme aprobar el alcance antes
de editar. Tras aprobarlo, actualiza contrato, plataformas afectadas, controles, pruebas y docs.
Indica el impacto de versión y añade el changeset necesario. Crea un commit local y espera sin
hacer push ni PR.
```

### Mejorar la apariencia

Separa un ajuste visual de una nueva API pública de personalización.

```text
Pule la apariencia de [componente]. Problema actual: [qué se ve mal].
Resultado deseado: [descripción o referencia adjunta]. Mantén el comportamiento y la API existentes.

Revisa los tokens y puntos de personalización actuales; propón el ajuste coherente más pequeño.
Si requiere una prop, token, dependencia o comportamiento nuevo, explícalo y pregunta antes de
ampliar el alcance. Comprueba claro/oscuro, al menos dos temas, pantallas estrechas/anchas y los
estados de foco/deshabilitado relevantes en las demos web y nativa afectadas. Actualiza los
ejemplos visuales necesarios, valida y crea un nuevo commit local de revisión. No hagas push.
```

### Planificar un cambio incompatible

```text
Estoy valorando cambiar [API actual] por [API deseada] en [componente].
Investiga las alternativas e indica consumidores/plataformas afectados, pasos de migración,
impacto de versión y una opción compatible si existe. No edites archivos todavía. Pídeme elegir
el enfoque antes de implementar un cambio incompatible.
```

## Diagnosticar y corregir

### Reproducir y corregir un bug

Da hechos observables; una causa sospechada es una hipótesis, no una condición para la solución.

```text
Corrige este bug en [componente] sin rediseñar su API.
Entorno: [framework/plataforma, versiones relevantes, navegador o dispositivo].
Reproducción: [pasos mínimos numerados o ejemplo adjunto].
Esperado: [comportamiento observable].
Actual: [comportamiento observable y error/log relevante].
Frecuencia: [siempre, intermitente o condiciones conocidas].

Reprodúcelo primero y encuentra la causa raíz. Si no puedes reproducirlo, explica qué información
falta en vez de adivinar. Añade una regresión concreta que falle antes del arreglo y pase después,
preserva el comportamiento existente y revisa la integración/consola de la plataforma afectada.
Si la solución requiere cambiar la API o el alcance, pregunta antes. Valida, crea un commit local
y muéstrame las evidencias y los pasos para volver a probarlo. Espera sin hacer push ni PR.
```

### Recuperar la paridad

```text
[Componente] se comporta distinto entre [plataforma A] y [plataforma B].
El contrato compartido indica [regla esperada]. Reprodúcelo con [pasos o ejemplo].

Compara ambas implementaciones y su integración de wrappers/eventos. Corrige la causa específica
sin duplicar comportamiento en los adaptadores. Si la diferencia es intencional o el contrato
no la resuelve, explica las opciones y pregúntame antes de cambiarlo. Prueba la integración,
controles y consola afectados. Separa React Native Web, tests con mocks, builds nativos y resultados
en dispositivos reales; declara los entornos no disponibles. Crea un commit local y espera mi revisión.
```

## Mejorar evidencias y ejemplos

### Actualizar documentación y demos

```text
Mejora las docs y demos de [componente] sin añadir comportamiento nuevo al componente.
Caso de uso que quiero explicar: [tarea del usuario].
Ejemplos/controles ausentes o confusos: [observaciones].

Revisa primero el contrato real. Mantén las tablas y snippets generados vinculados a él; muestra
uso normal, estados relevantes, personalización y limitaciones, no solo el aspecto por defecto.
Actualiza las páginas EN/ES y los controles aplicables del Playground/demo nativa. Prueba los
ejemplos y controles en los entornos disponibles, revisando teclado, cambios de estado y consola.
Informa de carencias del contrato o controles en vez de inventar una API. Valida los archivos
afectados, crea un commit local y espera mi revisión.
```

### Revisar sin cambiar archivos

```text
Usa reviewer para revisar [componente o rama actual] frente a develop y al alcance aceptado.
Busca problemas de funcionamiento, accesibilidad, paridad de API/plataformas, controles
representativos, coste del bundle y evidencias de ejecución ausentes. Informa solo de hallazgos
accionables de alta confianza con ubicación, gravedad y pasos de reproducción cuando sea posible.
Distingue los fallos reales de las comprobaciones no disponibles.
No edites archivos, no hagas commit ni push y no abras una PR.
```

Para una revisión centrada en accesibilidad, añade el escenario de teclado, etiquetado, foco,
movimiento o lector de pantalla relevante. Las comprobaciones automáticas no prueban por sí solas
la accesibilidad.

### Añadir pruebas concretas

```text
Añade cobertura concreta para [componente], usando add-contract-tests cuando corresponda.
Comportamiento sin cubrir: [escenario y resultado esperado según el contrato aceptado].
Cubre la integración de plataformas y casos límite relevantes, no detalles internos ni getters
triviales. No cambies la API ni persigas un porcentaje de cobertura. Si las pruebas descubren
un bug de comportamiento, infórmalo y acuerda el alcance del arreglo antes de ampliar esta tarea.
Ejecuta los tests y comprobaciones requeridas, distingue mocks de evidencias de ejecución,
crea un commit local y espera sin hacer push ni PR.
```

## Otras tareas de la librería

### Añadir un tema o token

```text
Usa design-system con add-theme/add-token según corresponda.
Necesito [objetivo visual y usos afectados]. Comprueba primero si los temas/tokens actuales ya lo
resuelven. Recomienda opciones para claro/oscuro, roles semánticos, paridad web/nativo y
accesibilidad; pregúntame antes de añadir tokens públicos o decidir el diseño. Tras aprobarlo,
usa el generador para un tema nuevo, valida contraste sin bajar umbrales, actualiza galerías/docs
y añade el changeset necesario. Crea un commit local y espera mi revisión.
```

### Crear una gráfica

```text
Crea [tipo de gráfica] siguiendo create-chart para [estructura de datos y pregunta del usuario].
Investiga primero representaciones accesibles, interacciones, límites de datos y diferencias
web/nativo. Recomienda un alcance inicial y pregúntame por ejes, etiquetas, estados vacíos/de error,
personalización, texto/tabla alternativos e interacciones antes de generar archivos.
Tras aprobarlo, implementa el layout puro compartido y los renderizadores aplicables, ejemplos
y pruebas. Informa del coste del bundle y separa las evidencias de ejecución de los builds.
Crea un commit local y espera sin hacer push ni PR.
```

## Continuar la conversación

Son **mensajes separados para cada momento**, no líneas para añadir al prompt inicial.
Sustituye `[SHA]` por el commit exacto presentado para revisión local.

### Aceptar el alcance propuesto

```text
Apruebo el alcance que acabas de resumir, con sus exclusiones y comprobaciones aplazadas.
Implementa ese acuerdo y ejecuta las pruebas. Si cambia una decisión relevante de API, diseño
o dependencias, vuelve a preguntarme. Termina con un commit local y espera; esto no autoriza push ni PR.
```

### Pedir otra iteración

```text
Probé el commit [SHA]. Cambia [observación concreta] para que [resultado esperado].
Mantén el resto del alcance aceptado. Valida el ajuste, crea un nuevo commit en esta rama de
trabajo sin modificar los anteriores con amend y espera a que revise el nuevo SHA. No hagas push.
```

### Subir el commit aceptado y abrir la PR

Úsalo solo después de comprobar la implementación y sus limitaciones declaradas.

```text
Apruebo el commit revisado [SHA] y sus limitaciones declaradas. Usa open-pr para verificar la
identidad, que HEAD no haya cambiado y las evidencias de validación; haz push y abre o actualiza
su PR a develop. Informa de la URL y del estado real de los checks. No hagas merge ni publiques.
```

### Retomar en otro chat

```text
Retoma [tarea] en la rama [rama], commit [SHA]. Lee el diseño aceptado, el diff actual y las
evidencias de validación: [ubicaciones o resumen de entrega anterior].
Resume lo terminado, pendiente y no verificado antes de continuar. Este mensaje no autoriza
alcance ni push; vuelve a preguntar si no puedes recuperar el acuerdo o las evidencias anteriores.
```

Para el proceso completo de entrega, consulta el [flujo de Git](../git-workflow/) y
[versiones y publicación](../publishing/). Abrir una PR de trabajo no equivale a pedir una release.
