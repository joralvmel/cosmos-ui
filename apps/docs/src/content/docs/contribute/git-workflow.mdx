## Branches

| Branch | Purpose | How changes arrive |
| --- | --- | --- |
| `main` | Released code; every push runs the release and docs deployment | Merge commit from `develop` (release pull request) |
| `develop` | Integration, default branch | Squash merge of work branches |
| `<type>/<scope>-<description>` | One task | Created from `develop`, deleted after merge |

Types: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`. Scope: package or area (`elements`, `tokens`,
`docs`…). Example: `feat/elements-switch`. Contributors without write access fork the repository and
open the pull request from their fork.

## Commits

- [Conventional Commits](https://www.conventionalcommits.org/): `type(scope): summary`, several scopes
  separated by commas (`feat(mcp,cli): …`). The `commit-msg` hook checks it.
- Use your own Git identity; prefer your GitHub noreply email. Sign off with `git commit -s`
  ([DCO](https://developercertificate.org/)) if you can.
- Never use `--no-verify`.

## Pull requests

1. `start-work` creates a local branch from synchronized `develop`. Component work follows the
   [research and scope approval workflow](../working-with-agents/#research-decisions-and-local-review).
2. `finish-work` validates, automatically commits locally, reports the SHA and local test steps,
   then **waits without push or PR**. Requested changes get a new commit and another review pause;
   previous commits are not amended by default.
3. Explicit acceptance of that unchanged HEAD authorizes `open-pr` to verify identity, push and
   open/reuse the PR to `develop`. Initial task or scope approval does not accept unseen changes.
   New commits on an already open PR require the same local review before push.
4. Required: green checks (lint, terms, typecheck, tests, build, packs, docs build, changeset, commit
   hygiene) and resolution of review conversations. Approvals are optional.
5. Squash merge: the pull request title must be a Conventional Commit (checked by CI).
6. `sync-after-merge` cleans up the local branch.

Approvals are optional on `main` and `develop` so a sole maintainer can merge their own pull requests.
This policy applies to all contributors: classic branch protection on a personal repository does not
support individual review exemptions. Pull requests, required checks and conversation resolution
remain mandatory. Copilot reviews are advisory, not approving reviews.
The agent's local review pause is separate from GitHub review requirements; it changes no branch
protection settings. Agents never merge or publish just because local changes were accepted.

## Releases

`release-pr` opens `develop → main` with the pending changesets; merge it with a merge commit. The
[Release and publishing](../publishing/) page explains the rest.

## Repository settings

Branch protection, merge options and labels are code: `npm run setup-repo` shows the changes and
`npm run setup-repo -- --apply` applies them with the GitHub CLI. Settings that only exist in the
GitHub UI are printed at the end of the command.

## Personal safeguards (optional)

On a computer with several GitHub accounts, create `.local/git-identity.json` (ignored by Git) with
your name, email and GitHub login: the `pre-commit` hook and the `verify-identity` skill then block
commits and pushes with another identity. On a computer with a single personal account nothing is
needed.
