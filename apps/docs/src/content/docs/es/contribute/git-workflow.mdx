## Ramas

| Rama | Propósito | Cómo llegan los cambios |
| --- | --- | --- |
| `main` | Código publicado; cada push ejecuta la release y el despliegue de la documentación | Merge commit desde `develop` (pull request de release) |
| `develop` | Integración, rama por defecto | Squash merge de las ramas de trabajo |
| `<tipo>/<ámbito>-<descripción>` | Una tarea | Se crea desde `develop` y se borra tras integrarla |

Tipos: `feat`, `fix`, `docs`, `chore`, `refactor`, `test`. Ámbito: paquete o área (`elements`, `tokens`,
`docs`…). Ejemplo: `feat/elements-switch`. Quien no tiene permisos de escritura hace un fork y abre el
pull request desde él.

## Commits

- [Conventional Commits](https://www.conventionalcommits.org/): `tipo(ámbito): resumen`, varios ámbitos
  separados por comas (`feat(mcp,cli): …`). Lo comprueba el hook `commit-msg`.
- Usa tu propia identidad de Git; mejor tu email noreply de GitHub. Firma con `git commit -s`
  ([DCO](https://developercertificate.org/)) si puedes.
- Nunca uses `--no-verify`.

## Pull requests

1. `start-work` crea una rama local desde `develop` sincronizada. Para componentes se sigue el
   [flujo de investigación y aprobación de alcance](../working-with-agents/#investigación-decisiones-y-revisión-local).
2. `finish-work` valida, crea automáticamente un commit local, muestra el SHA y los pasos para
   probarlo, y **espera sin push ni PR**. Los ajustes generan otro commit y otra pausa de revisión;
   no se modifican los commits anteriores con amend por defecto.
3. La aceptación explícita de ese HEAD sin cambios permite a `open-pr` verificar la identidad,
   hacer push y abrir o reutilizar la PR a `develop`. La petición inicial o la aprobación del
   alcance no aceptan cambios aún no vistos. Los nuevos commits de una PR abierta pasan por la
   misma revisión local antes del push.
4. Obligatorio: checks en verde (lint, términos, typecheck, tests, build, paquetes, build de la
   documentación, changeset, higiene de commits) y resolver las conversaciones de revisión. Las
   aprobaciones son opcionales.
5. Squash merge: el título del pull request debe ser un Conventional Commit (lo comprueba la CI).
6. `sync-after-merge` limpia la rama local.

Las aprobaciones son opcionales en `main` y `develop`, para poder integrar los propios pull requests
sin otro mantenedor. Esta política se aplica a todos los colaboradores: la protección clásica de un
repositorio personal no admite excepciones individuales de revisión. Los pull requests, los checks
obligatorios y la resolución de conversaciones siguen siendo obligatorios. Las revisiones de Copilot
son orientativas, no aprobaciones.
La pausa de revisión local del agente es independiente de las aprobaciones de GitHub y no cambia la
protección de ramas. Aceptar los cambios locales no autoriza al agente a integrar ni publicar.

## Releases

`release-pr` abre `develop → main` con los changesets pendientes; intégralo con un merge commit. La
página [Versiones y publicación](../publishing/) explica el resto.

## Configuración del repositorio

La protección de ramas, las opciones de merge y las etiquetas son código: `npm run setup-repo` muestra
los cambios y `npm run setup-repo -- --apply` los aplica con la GitHub CLI. Los ajustes que solo existen
en la interfaz de GitHub se imprimen al final del comando.

## Protecciones personales (opcional)

En un ordenador con varias cuentas de GitHub, crea `.local/git-identity.json` (ignorado por Git) con tu
nombre, email y login de GitHub: el hook `pre-commit` y la skill `verify-identity` bloquean entonces los
commits y pushes con otra identidad. En un ordenador con una sola cuenta personal no hace falta nada.
