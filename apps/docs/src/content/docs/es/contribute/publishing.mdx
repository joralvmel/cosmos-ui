Para prompts de planificación, revisión de PRs, verificación, recuperación y sincronización,
consulta [releases y mantenimiento](../prompt-cookbook/#releases-y-mantenimiento).

Cosmos UI usa [Changesets](https://github.com/changesets/changesets) para las versiones y los
changelogs, y publica en el registro público de npm con
[trusted publishing](https://docs.npmjs.com/trusted-publishers) (OIDC, sin token de npm) y
[provenance](https://docs.npmjs.com/generating-provenance-statements).

## Cómo funcionan las releases

<Steps>

1. Cada pull request que cambia `packages/*` añade un changeset (`npm run changeset`).
2. Cuando `develop` está listo, un mantenedor ejecuta `npm run deps:changeset` (changesets patch
   para las actualizaciones de dependencias de runtime fusionadas desde Dependabot), abre el pull
   request de release `develop → main` (skill `release-pr`) y lo integra con un **merge commit**.
3. En `main`, el workflow `Release` abre o actualiza el pull request **Version Packages**: sube las
   versiones y escribe los changelogs.
4. Al integrar **Version Packages** se ejecuta `changeset publish`: las nuevas versiones se publican en
   npm con provenance, se suben los tags de Git y se crea una GitHub Release por paquete.
5. El workflow `Docs` despliega el sitio de documentación desde `main`.
6. Sincroniza el `main` publicado con `develop` mediante una PR con **merge commit**, nunca
   squash/rebase. Tras actualizar los remotos, verifica que
   `git merge-base --is-ancestor origin/main origin/develop` termine correctamente. Igualar los
   archivos no basta: conservar el historial evita conflictos repetidos.

</Steps>

`release-pr` distingue una evaluación de solo lectura de la preparación. Preparar incluye arreglos
locales seguros de sincronización, changesets de dependencias y conflictos, con validación y commit
local para revisar antes del push. Continúa tras integrar las PRs previas; el merge y la publicación
siguen necesitando aprobación explícita. Usa [el prompt de preparación](../prompt-cookbook/#preparar-y-abrir-la-pr-de-release).

Prereleases: ejecuta a mano el workflow `Release` sobre `develop` (Actions → Release → Run workflow).
Publica un snapshot como `0.2.0-next-20261110120000` con el dist-tag `next`:

```bash
npm install @joralvmel/cosmos-react@next
```

## Configuración inicial (mantenedores)

La skill `publish-setup` guía a un agente por la misma lista.

<Steps>

1. **Cuenta de npm.** Crea una cuenta en [npmjs.com](https://www.npmjs.com/signup), verifica el email y
   activa la autenticación en dos pasos (Account → Two-Factor Authentication, "Authorization and
   writes"). El scope `@joralvmel` es el scope de usuario de la cuenta.

2. **Comprueba los paquetes.**

   ```bash
   npm ci
   npm run check-packs     # compila, valida los manifiestos y ejecuta npm pack --dry-run
   npm run publish-order   # primero las dependencias
   ```

3. **Primera publicación a mano.** Trusted publishing solo se puede configurar en paquetes que ya
   existen. Publica una vez la versión actual de cada paquete, en el orden mostrado:

   ```bash
   npm login
   cd packages/core && npm publish --access public --otp <código> && cd ../..
   # …repite para cada paquete en orden
   ```

   La primera versión es un marcador (`0.0.0`); puedes marcarla con
   `npm deprecate @joralvmel/cosmos-core@0.0.0 "placeholder"`.

4. **Trusted publisher por paquete.** En npmjs.com abre cada paquete → Settings → Trusted Publisher →
   GitHub Actions e indica: owner `joralvmel`, repositorio `cosmos-ui`, workflow `release.yml`, entorno
   `npm`. Después, en "Publishing access", elige
   "Require two-factor authentication and disallow tokens".

5. **GitHub.** En la configuración del repositorio:
   - Environments → crea `npm` (opcionalmente con revisores obligatorios).
   - Secrets and variables → Actions → Variables: `COSMOS_PUBLISH_ENABLED` = `true`.
   - Para el sitio de docs: Pages → Source "GitHub Actions" y la variable `COSMOS_DOCS_ENABLED` = `true`.

6. **Verifica** tras la primera release automática:

   ```bash
   npm view @joralvmel/cosmos-core versions dist-tags
   npm audit signatures   # dentro de un proyecto que haya instalado los paquetes
   ```

   La página del paquete en npmjs.com muestra la insignia de provenance enlazada a la ejecución del
   workflow.

</Steps>

## Mantenimiento de dependencias

| Qué | Automatización | Tu parte |
| --- | --- | --- |
| Actualizaciones minor/patch | Dependabot abre PRs agrupadas hacia `develop` cada lunes (stack fijado: solo patches) | Revisarlas e integrarlas |
| Clasificación | La CI (`Changeset present`) marca cada actualización como de desarrollo, de runtime o pendiente de decisión | Majors, rangos de peer y el stack fijado necesitan un changeset en la PR, normalmente con `upgrade-stack` |
| Actualizaciones de runtime | Se aplazan a la release; la PR de release falla hasta que estén cubiertas | `npm run deps:changeset` en `develop` antes de `release-pr` |
| Dependencias nuevas | `Dependency review` bloquea vulnerabilidades altas/críticas y licencias fuera de la lista permitida | Elegir otro paquete o discutir una excepción |
| Vulnerabilidades | Alertas y PRs de seguridad de Dependabot; `Security audit` semanal mantiene una issue `security` | Corregir con un patch o planificar un `upgrade-stack` |
| Majors y stack fijado | `Dependency report` mensual mantiene una issue `dependencies` | Planificar la actualización con `upgrade-stack` |
| Auto-merge de herramientas | Opcional: con la variable `COSMOS_DEPENDABOT_AUTOMERGE` = `true`, las minor/patch de herramientas de desarrollo se integran solas cuando pasan los checks | Nada, o dejarlo desactivado para revisarlo todo |

Ejecuta los informes en local con `npm run deps:audit` y `npm run deps:outdated`. Los merges del
auto-merge usan el token del workflow, así que no lanzan workflows en `develop`; la siguiente pull
request o release ejecuta todos los checks. Prompts: [mantener las dependencias al día](../prompt-cookbook/#mantener-las-dependencias-al-día).

## Solución de problemas

| Síntoma | Solución |
| --- | --- |
| La promoción de release tiene conflictos tras una sincronización anterior | Comprueba el historial, no solo la igualdad de archivos. Prepara un arreglo de sincronización con `release-pr`; conserva los metadatos publicados y el trabajo nuevo de develop, regenera el lockfile con npm y fusiona la sincronización con merge commit. |
| La protección de historial lineal bloquea el merge commit de sincronización | Con aprobación del mantenedor, aplica la política revisada de `setup-repo`. Permite merge commits conservando PRs, checks obligatorios y protecciones contra force-push y borrado. No uses squash como atajo. |
| La PR de release falla en "Released runtime dependency updates have changesets" | Ejecuta `npm run deps:changeset` en una rama de trabajo de `develop` e intégrala antes de la release. |
| Una PR de Dependabot falla en "Classify dependency updates" | Necesita una decisión: revísala con `upgrade-stack` y añade un changeset a la PR. |
| `E404` / `ENEEDAUTH` al publicar | El trusted publisher no coincide: revisa owner, repositorio, nombre del workflow y entorno. |
| No aparece el pull request "Version Packages" | Permite que GitHub Actions cree pull requests (`npm run setup-repo -- --apply` lo hace). |
| Workflow omitido | `COSMOS_PUBLISH_ENABLED` no es `true`. |
| Falla `check-packs` | A un manifiesto le falta `publishConfig.access`, `files`, `exports`, `repository`, `license` o `llms.md`. |
