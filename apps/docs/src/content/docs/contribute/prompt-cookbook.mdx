Use these prompts in the **main chat opened in this repository**. It coordinates the specialists;
you do not need to switch agents for each step. Natural-language prompts work without a slash
command. Names such as `create-component` refer to existing skills, not new commands.

Replace the values in `[brackets]` and attach relevant files, screenshots, issue links or logs.
Remove anything that does not apply; never paste credentials or private data into a prompt.

### What every implementation includes

The [component workflow](https://github.com/joralvmel/cosmos-ui/blob/develop/docs/conventions/component-workflow.md)
already requires research-led scope approval for new behavior, contract/platform parity,
appropriate tests, EN/ES docs, AI references and changesets for changed publishable packages.
An exact bug fix within the accepted contract does not need another feature interview.

Implementation ends with a validated **local commit and a pause**. Neither the initial prompt nor
scope approval authorizes push, PR, merge or release. Read-only research/review does not authorize
edits or commits. If a browser, device or tool is unavailable, the agent must report it rather than
call the check passed.

## Start a component

### Explore the backlog

Use this when you want advice, not implementation yet.

```text
Check the current component inventory and its dependencies. Recommend three candidates to build
next, ordered by usefulness, effort and what they unblock. Research the most promising candidate
and distinguish required, recommended and optional features, with sources and platform differences.
Present the decisions I should make next. This is read-only: do not generate files, commit or push.
```

### Create from a need

`badge` is an example, not a request to add every feature mentioned in the research.

```text
Create the badge component using create-component. The goal is to communicate a short status or
count in web, React, Angular and React Native.

Check the inventory and research first. Recommend a useful initial scope, then ask me about
variants, sizes, customization, content, accessibility and platform differences in small batches.
Explain what should be included, excluded or deferred; wait for my approval before generation
or contract edits.

After approval, implement and validate the agreement end-to-end, including representative demo
controls. Create a local commit, show its SHA and how to try it, then wait without push or PR.
```

### Create from a design

A screenshot does not specify keyboard behavior, state ownership or all native interactions.

```text
Use component-from-design for [component] with this reference: [Figma frame link or screenshot].
The intended use is [user need]. Check whether an existing component already solves it.

Research the interaction pattern and map the design to current tokens. Show what the reference
defines, what is missing and which platform differences need a decision. Ask me before choosing
unseen behavior or adding tokens/dependencies. Wait for scope/design approval, then complete the
accepted component on every applicable platform. Validate, commit locally and pause for my review.
```

## Use a reference project

Use an existing React, React Native or other UI project as **evidence**, not as a library to copy.
The [reference-project convention](https://github.com/joralvmel/cosmos-ui/blob/develop/docs/conventions/reference-projects.md)
keeps sources read-only, checks the real stack and separates generic UI from application logic.
No new package or agent is needed: the skill coordinates existing research/design/platform roles.

### Analyze themes and components

```text
Use adapt-reference-project with [reference folders or public links]. You may inspect relevant
UI/theme files read-only. Focus on [theme, components or user need]; target [platforms].
Do not run source scripts, install dependencies, read environment files or change those projects.

Check the actual stack, ownership/license constraints, theme definitions, representative primitives
and their usages. Compare with current Cosmos tokens, contracts and inventory. Return a theme map,
a component map (reuse/extend/create/compose/keep in app) and a prioritized migration plan.
Distinguish supported mappings from gaps, generic UI from business logic and web from native.
Keep source identity, private paths, code and branded assets out of tracked output.

Recommend one first slice and ask informed design/API questions after research. This is analysis
only: do not generate files, implement, commit or push.
```

### Implement an approved slice

Send this after reviewing the maps and resolving the proposed decisions, not as blanket permission
to import an entire project. Themes distinguish identity from light/dark mode. Existing seeds and
radius presets do not imply arbitrary typography, spacing or motion scales are supported.

```text
I approve [specific theme/component slice] from the analysis, with [accepted choices],
excluding [out of scope] and deferring [limitations]. Use adapt-reference-project to hand off to
add-theme/add-token or create-component/modify-component as appropriate.

Implement independently in Cosmos with neutral examples. Preserve existing token semantics,
contracts and accessibility; explain any visual deviations needed for contrast or platforms.
Use the generator when required, complete applicable platforms, examples, EN/ES docs, AI references,
tests and changesets. Reopen approval for unsupported token roles or meaningful API/dependency gaps.
Keep reference/consumer projects unchanged. Validate, commit locally and pause without push or PR.
```

### Plan gradual consumer replacement

Cosmos React wraps web components; React Native uses its dedicated implementation. Shared contracts
do not make either one a drop-in replacement for another project's props or providers.

```text
Plan replacing [consumer theme/components] with Cosmos after [approved slice] is released.
Inspect the authorized consumer UI files read-only. Check installed versions, providers,
styling, imports, forms/events, SSR/client boundaries and native/Expo compatibility as applicable.
Identify stable replacements, unsupported capabilities and temporary coexistence needs.
Give a small migration order, acceptance checks and rollback per step. Do not edit the consumer
or Cosmos, install packages, execute consumer code, commit or push. Ask before implementing any step.
```

## Evolve an existing component

### Extend behavior

Describe the user outcome before prescribing a prop name. If the capability already exists,
the agent should explain how to use it instead of creating another API.

```text
Use modify-component for [component]. I need users to be able to [desired outcome].
Example scenario: [input, interaction and expected result].

Check the current API, scenarios and docs first. If this is already supported, show me how and
do not make unnecessary changes. Otherwise research alternatives, recommend an API and explain
compatibility, accessibility and web/native trade-offs. Ask me to approve the scope before edits.
After approval, update the contract, affected platforms, controls, tests and docs. State the
versioning impact and add the required changeset. Commit locally and wait without push or PR.
```

### Improve appearance

Separate a visual adjustment from a new public customization API.

```text
Polish the appearance of [component]. Current issue: [what looks wrong].
Desired result: [description or attached reference]. Keep its existing behavior and public API.

Inspect the current tokens and styling hooks; propose the smallest coherent adjustment. If it
requires a new prop, token, dependency or behavior, explain it and ask before expanding the scope.
Check light/dark, at least two themes, narrow/wide layouts and relevant focus/disabled states
in the affected web and native demos. Update visual examples as needed, validate and create
a new local review commit. Do not push.
```

### Plan a breaking change

```text
I am considering changing [current API] to [desired API] in [component].
Research the alternatives and report affected consumers/platforms, migration steps, versioning
impact and a compatible option if one exists. Do not edit files yet. Ask me to choose the approach
before implementing a breaking change.
```

## Diagnose and fix

### Reproduce and fix a bug

Give observable facts; a suspected cause is a hypothesis, not a constraint on the fix.

```text
Fix this bug in [component] without redesigning its API.
Environment: [framework/platform, relevant versions, browser or device].
Reproduction: [minimal numbered steps or attached example].
Expected: [observable behavior].
Actual: [observable behavior and relevant error/log].
Frequency: [always, intermittent or known conditions].

Reproduce it first and find the root cause. If you cannot reproduce it, explain the missing
information rather than guessing. Add a focused regression that fails before the fix and passes
after it, preserve existing behavior and check the affected platform integration/console.
If the fix requires an API or scope change, ask first. Validate, commit locally and show me
the evidence and retry steps. Wait without push or PR.
```

### Restore platform parity

```text
[Component] behaves differently between [platform A] and [platform B].
The shared contract says [expected rule]. Reproduce using [steps or example].

Compare both implementations and their wrapper/event integration. Fix the platform-specific
cause without duplicating behavior in adapters. If the difference is intentional or the contract
does not resolve it, explain the options and ask me before changing it. Test the affected
integration, controls and console. Separate React Native Web, mocked tests, native builds and
actual device results; disclose unavailable environments. Commit locally and pause for review.
```

## Improve evidence and examples

### Update documentation and demos

```text
Improve the docs and demos for [component] without adding new component behavior.
Use case to explain: [user task]. Missing or confusing examples/controls: [observations].

Check the real contract first. Keep generated API tables/snippets tied to it; show normal use,
relevant states, customization and limitations rather than only the default appearance.
Update EN/ES pages and applicable Playground/native demo controls. Try the examples and controls
in the available environments, checking keyboard, state changes and console diagnostics.
Report any contract/control gap instead of silently inventing an API. Validate the affected
files, create a local commit and wait for my review.
```

### Review without changing files

```text
Use reviewer to inspect [component or current branch] against develop and the accepted scope.
Focus on correctness, accessibility, API/platform parity, representative controls, bundle impact
and missing runtime evidence. Report only actionable, high-confidence findings with file locations,
severity and reproduction steps where possible. Separate actual failures from unavailable checks.
Do not edit files, commit, push or open a PR.
```

For an accessibility-focused review, add the relevant keyboard, labeling, focus, motion or
screen-reader scenario. Automated checks alone do not prove accessibility.

### Add focused tests

```text
Add focused coverage for [component] using add-contract-tests where applicable.
Missing behavior: [scenario and expected result from the accepted contract].
Cover relevant platform integration and edge cases, not implementation details or trivial getters.
Do not change the API or chase a coverage percentage. If the tests expose a behavior bug, report it
and agree the fix scope before expanding this task. Run the tests and required checks, distinguish
mocks from runtime evidence, commit locally and pause without push or PR.
```

## Other library work

### Add a theme or token

```text
Use design-system with add-theme/add-token as appropriate. I need [visual goal and affected uses].
First check whether current themes/tokens already solve it. Recommend options for light/dark,
semantic roles, web/native parity and accessibility; ask me before adding public tokens or choosing
the design. After approval, use the generator for a new theme, validate contrast without lowering
thresholds, update galleries/docs and add the required changeset. Commit locally and pause for review.
```

### Create a chart

```text
Create [chart type] using create-chart for [data shape and user question].
Research accessible representations, interactions, data limits and web/native trade-offs first.
Recommend an initial scope and ask me about axes, labels, empty/error states, customization,
alternative text/table and any interaction before generation.
After approval, implement the pure shared layout and applicable renderers, examples and tests.
Report bundle costs and actual runtime evidence separately from builds. Commit locally and wait
without push or PR.
```

## Release and maintenance

A work PR goes to `develop`; releasing is a separate decision. The stable flow is
`develop → main` (merge commit), then the generated **Version Packages** PR, then publication.
See [release and publishing](../publishing/) for setup and commands. These prompts do not authorize
automatic merges, changes to publishing permissions, or a release while work is still unmerged.

### Plan the next release

```text
Assess whether develop is ready for a stable release. This is read-only.
Check the current remote state, merged work, CI and pending changesets against origin/main.
List affected packages, expected bumps, breaking changes/migration notes and missing evidence.
Distinguish package changes from private docs/tooling changes that need no changeset.
Recommend release now or remaining work. Do not change versions/changelogs, dispatch workflows,
open or merge PRs, push tags or publish.
```

### Open the release PR

```text
I authorize opening the release PR for the already merged changes on develop.
Use release-pr: verify identity, remote, green checks and pending changesets. Reuse an existing
open develop-to-main release PR; stop on conflicts or missing evidence. Summarize packages,
bumps, highlights and migration notes, and report its URL/checks.
Do not merge it, edit versions/changelogs manually or publish. Wait for my review; when approved,
the release promotion must use a merge commit, not squash.
```

### Review Version Packages

```text
Review the generated Version Packages PR [URL] without editing or merging.
Compare its versions, dependency updates and changelogs with the accepted changesets and current
release history. Check CI and identify missing/unexpected packages, bumps or migration notes.
Explain what merging it will publish and which approvals remain. Do not publish, dispatch workflows
or alter generated files; report blockers and wait for my decision.
```

### Verify publication and try it as a consumer

```text
Verify the release [version or workflow URL] without changing the repository.
Check actual workflow results, npm versions/dist-tags and provenance, Git tags/GitHub Releases,
and the docs deployment. Separate published, pending and failed packages; green CI alone is not
proof that npm publication succeeded.
Give exact install/version and smoke-test steps for [React/Angular/web/React Native] using published
packages in an isolated consumer, not workspace links. Do not install or modify that consumer yet.
Report remaining compatibility/runtime checks rather than claiming they passed.
```

### Diagnose a failed publication

```text
Diagnose the failed release [workflow URL and relevant error]. Inspect the run and package state
read-only first. Identify the root cause and whether some packages/tags were already published.
Do not blindly rerun, delete/reuse published versions, weaken permissions, change registry settings
or expose credentials. Propose the smallest recovery and ask for approval before changes or retry.
Any code fix needs validation, a new local review commit and a pause before push.
```

### Try a snapshot before stable release

```text
Assess a next-tag snapshot for [merged scope] using release. Check workflow inputs, current branch,
CI and package state first. Explain the exact dispatch, expected versions/dist-tag and install
commands; distinguish snapshot publication from a stable release.
Do not dispatch or publish until I explicitly approve that operation. Do not move latest or create
stable release tags. Report unavailable checks and the cleanup/migration plan for test consumers.
```

### Synchronize after merge or release

```text
Synchronize after [merged work/release PR URL] using sync-after-merge.
Check identity, remote state and local changes first; preserve unrelated work and never force-push.
Confirm the PR really merged before removing its work branch. If Version Packages left main ahead
of develop, explain the sync diff and open/reuse the main-to-develop synchronization PR only;
do not merge it automatically. Stop on conflicts or decisions that change code.
Report final branch/HEAD and anything still pending. Do not start another component or release.
```

## Continue the conversation

These are **separate messages at the appropriate stage**, not lines to append to the initial prompt.
Replace `[SHA]` with the exact commit presented for local review.

### Accept the proposed scope

```text
I approve the scope you just summarized, including its exclusions and deferred checks.
Implement that agreement and run the checks. If a meaningful API, design or dependency decision
changes, ask me again. Finish with a local commit and pause; this does not authorize push or PR.
```

### Request another iteration

```text
I tried commit [SHA]. Change [specific observation] to [expected result].
Keep the rest of the accepted scope. Validate the adjustment, create a new commit on this work
branch without amending earlier commits, and wait for me to review the new SHA. Do not push yet.
```

### Push the accepted commit and open the PR

Use this only after checking the implementation and its reported limitations.

```text
I approve the reviewed commit [SHA] and its disclosed limitations. Use open-pr to verify identity,
unchanged HEAD and validation evidence, push it and open or update its PR to develop.
Report the URL and actual check status. Do not merge or publish.
```

### Resume in another chat

```text
Resume [task] on branch [branch] at commit [SHA]. Read the accepted design, current diff and
validation evidence: [file locations or previous handoff].
Summarize what is done, pending and unverified before continuing. Do not infer scope or push
approval from this message; ask again if the previous agreement/evidence cannot be recovered.
```

For the complete delivery process, see [Git workflow](../git-workflow/) and
[release and publishing](../publishing/). Opening a work PR is not a request to create a release.
