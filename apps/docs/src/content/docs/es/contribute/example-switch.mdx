Este recorrido añade `cosm-switch` (switch de WAI-ARIA) en todas las plataformas. Cada paso indica la
skill que se ejecuta (como `/prompt` en VS Code o pidiéndoselo al agente) y muestra los comandos que
lanza y la salida esperada.

## 1. Consultar el inventario — `component-status`

```bash
npm run status
```

```text
Components: 38 · stable 1 · in progress 0 · planned 37
…
planned      1  switch
…
Next suggested: icon, badge, avatar, divider, listbox
```

`switch` está planificado, tiene prioridad 1 y no tiene dependencias, así que puede empezar ya.

## 2. Issue y rama — `start-work`

```bash
git fetch origin
git switch develop
git pull --ff-only
git switch -c feat/elements-switch
```

```text
Switched to a new branch 'feat/elements-switch'
```

Si existe un issue relacionado (por ejemplo #12), se enlaza en la PR posterior. La rama de trabajo
se mantiene local hasta que aceptes la implementación.

## 3. Investigación — `research-reference`

El agente `researcher` resume el
[patrón switch de la APG](https://www.w3.org/WAI/ARIA/apg/patterns/switch/): rol `switch`,
`aria-checked`, <kbd>Espacio</kbd> alterna, etiqueta visible, y recomienda un
`<input type="checkbox" role="switch">` nativo dentro del Web Component (participación en formularios
sin coste).

También compara implementaciones públicas y separa los requisitos de los tamaños, estados y opciones
de personalización sugeridos. El chat principal pregunta qué incluir o aplazar, explica las
alternativas y resume el alcance y las pruebas de aceptación web/nativas. **Espera tu aprobación del
alcance y diseño antes de generar archivos o editar el contrato.**

## 4. Plan de API aceptado — `define-contract`

Tras la aceptación, `architect` plantea el contrato (por ejemplo props `checked`, `disabled`,
`required`, `name`, `value`, `label`; evento `change` → DOM `cosm-change`, React `onChange`, Angular
`(checkedChange)`, React Native `onCheckedChange`; estado `checked` con `defaultChecked`) y los
escenarios compartidos (alternar con puntero y teclado, deshabilitado, propuesta controlada sin aplicar).
Son decisiones ilustrativas, no una lista de funciones que se deba asumir. Los archivos del contrato
se completan tras generar el scaffold en el paso 6 y antes del comportamiento de cada plataforma.

## 5. Especificación visual — `design-component`

El agente `design-system` escribe `docs/design/switch.md`: tamaños de pista y control por `size`,
estados (hover, focus-visible, activado, deshabilitado, inválido), tokens (`--cosm-primary`,
`--cosm-border-strong`, `--cosm-surface`), animación con `prefers-reduced-motion`, y comprueba el
contraste en todos los temas.

## 7. React Native — `create-native-component`

`native-expert` implementa `Switch` con `Pressable`, `accessibilityRole="switch"`,
`accessibilityState={{ checked, disabled }}`, área táctil de 44 puntos y colores de `useTheme()`, y
completa la pantalla `apps/native-demo/app/switch.tsx`.

Las páginas siguen el orden de la anatomía (estado, Playground, variantes, estados, accesibilidad, API,
eventos por plataforma) en inglés y español. El Playground ya muestra código HTML, React, Angular y React

```bash

```


El inventario comprueba la estructura. Solo se marca `stable` al completar el alcance aceptado y las
pruebas requeridas, o si aplazas explícitamente pruebas no disponibles que siguen indicándose como
pendientes. La existencia de archivos no demuestra el funcionamiento en ejecución.

## 10. Changeset — `add-changeset`

```md
---
'@joralvmel/cosmos-core': minor

'@joralvmel/cosmos-react': minor
'@joralvmel/cosmos-angular': minor
'@joralvmel/cosmos-native': minor

Add the Switch component (`cosm-switch`) on every platform.
```

## 11. Revisión local y después pull request — `finish-work`, `open-pr`

```text
/finish-work "feat(elements): add cosm-switch" cierra #12
```

El agente ejecuta las comprobaciones del repositorio y las pruebas aplicables de navegador, wrappers
y nativo; verifica la identidad y crea automáticamente un commit local solo con los archivos de la
tarea. Comunica rama, SHA, matriz de resultados y cómo probarlo. **Se detiene sin push ni PR.**
Los mocks y las exportaciones no demuestran ejecución nativa; las pruebas o dispositivos no disponibles
siguen indicándose.

Prueba ese commit. Si pides ajustes, el agente valida y crea otro commit y vuelve a esperar.
No modifica el anterior con amend por defecto.

Solo después de aceptar el SHA revisado actual, `open-pr` verifica que HEAD no haya cambiado, hace
push y abre la PR a `develop` o reutiliza la PR abierta de esa rama. Por ejemplo:

```text
Apruebo el commit revisado <SHA>. Haz push y abre la PR a develop.
```

La CI ejecuta lint, términos, typecheck, tests y build, el build de la documentación (artefacto de
preview), la comprobación de changesets y la higiene de commits; el labeler añade `pkg:core`,
`pkg:elements`, `pkg:react`, `pkg:angular`, `pkg:native`, `app:docs` y `app:native-demo`.

## 12. Revisión e integración

Pide una revisión a `reviewer` y resuelve los hallazgos; las correcciones pasan por otro commit local
y tu aceptación antes del push. Las aprobaciones de GitHub son opcionales, pero los checks y la
resolución de conversaciones son obligatorios. El mantenedor integra con **Squash and merge** (el
título del PR se convierte en el mensaje del commit); la rama se borra sola. Aceptar los cambios locales
no autoriza una integración ni una release automática.

## 13. Volver a develop — `sync-after-merge`

```bash
git switch develop && git pull --prune --ff-only && git branch -D feat/elements-switch
```

## 14. Pull request de release — `release-pr`

```bash
npx changeset status --since=origin/main
gh pr create --base main --head develop --title "chore(release): switch" --label release
```

Intégralo con **Create a merge commit**.

## 15. Publicar — `release`

El workflow `Release` abre **Version Packages** en main (versiones `0.2.0`, changelogs). Al integrarlo
se publica en npm con provenance y se crean las GitHub Releases:

```bash
npm view @joralvmel/cosmos-elements version
```

```text
0.2.0
```
